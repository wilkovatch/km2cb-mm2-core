# AGENTS.md

Guidance for AI coding agents (and humans) working on the **Midtown Madness 2 core** of km2 City Builder. The core is installed in the builder's `Files/cores/MidtownMadness2`. Read the builder's [AGENTS.md](../../../AGENTS.md) first for the general rules (generic base builder, commits, versions, short tests, building, self-tests). [README.md](README.md) is the user-facing overview of the core; this file collects the MM2 facts and workflows that aren't obvious from the code.

## References

- MM2 file format specifications (needed for any change to the exporters): https://github.com/Dummiesman/angel-file-formats/tree/master/Midtown%20Madness%202. The PKG reference is https://github.com/Dummiesman/PKGImportExport.
- Machine-specific locations (the game install, the extracted stock data, the psdl-viewer) are in the builder's gitignored `CLAUDE.local.md`. Don't scan drives for them.

## Game data

Never commit original game data (`city/materials.csv`, stock `.pkg`/`.tex`/bounds, ...) to this repo. The user provides these files in the builder's gitignored `Files/common/MidtownMadness2/` folder, which mirrors the game layout (`geometry/`, `texture/`, `city/`, `jpg/`, `tune/banger/`) and is created from this core's `baseCommon/`, where only `_put ... here` placeholder files are tracked. When such a file is missing, warn and fall back to a default.

Do not put migrations information in the README, the migration process should be transparent to users.

The Scripts menu's **Import MM2 game assets** (`scripts/importGameAssets`) imports from the user's `MM2CORE.AR` and `MM2TEX.AR`. These are **DAVE**, not the ZIP archives written by `exporters/psdl/ar_packer.py`. The reader uses the index at `0x800`, padded index/name blocks and raw DEFLATE (`wbits=-15`) when stored and original sizes differ. It supports ASCII DAVE filenames only; `Dave` compressed filenames and ZIP mods are intentionally rejected. Format reference: https://github.com/EdnessP/scripts/blob/main/midnight-club/dave.py.

The importer selects only PKG/MTX geometry, TEX/TGA textures, banger tuning and `city/materials.csv`; no mods, loose overrides, bounds, city/race files or JPG/map frame. New paths are lowercase; existing paths are resolved case-insensitively. Destination is derived from the installed core, never the script's working directory. It skips existing files unless overwrite is checked, validates both archive indexes before writing, then publishes validated payloads through temporary sibling files and `os.replace`. Filesystem writes cannot be undone (`transaction: false`); cancellation kills Python and leaves completed files, possibly with a harmless `.km2-mm2-import-*.tmp` file. Reruns skip completed files. Save and reopen the city after importing to refresh asset caches.

Run the short synthetic tests with `python scripts/importGameAssets/_test_import_assets.py` from the core folder (standard library only). Test fixtures and outputs live in a temporary directory; use a writable `TMP`/`TEMP` if the sandbox's default temp directory is restricted. Stock checks should sample about ten entries with a fixed seed and compare them to the extracted data configured in the builder's local instructions; do not extract the entire game for a test. Helper/test filenames start with `_` so they cannot appear as separate Scripts-menu entries. Menu and runtime strings are in the script's `strings/en-US.json`.

## Coordinates

The builder and this core are left-handed, Y up, +Z forward, +X right. MM2 game files mirror X (MM2 x = -builder x, the exporters handle it). In-game north is -Z and east is +X.

## Self-contained exporter

Exporter changes affect the builder (C# and `Files/python`) and this core (`wilkovatch/km2cb-mm2-core`). `exporters/psdl/common` is ordinary tracked code vendored from `psdl-exporter-common`; keep its original license. There is no submodule or Blender compatibility requirement. BIN-only export and standalone writer tools remain supported.

When stashing to compare against old behaviour, stash both the builder repo and this repo. This repo keeps its own older stashes, so pop only yours.

Useful tools: `exporters/psdl/tools/psdl_check.py` (perimeter spikes/slits, prop-room texture indices), `bai_check.py --lint` (BAI sanity, max 11 roads per intersection), `decal_check.py`.

Fast exporter loop without the game (from the builder folder): `-- export-json <city> --out x.json`, then run this core's `exporters/psdl/export.py <Files/python> x.json x.psdl <flags...>` directly with the builder's `python/python.exe`. A BAI-only export of a large city takes about 3 s.

Exporter gotchas:
- The PSDL exporter waits for Enter only when stdin is a terminal, and tolerates EOF at that prompt. Linux console launches can inherit closed or redirected stdin; an optional pause must not turn a completed export into an error or mask a real failure. Without a console, the builder's `PythonManager.RunScriptTask` also feeds newlines on stdin for older exporters.
- A finished export deletes its `.bin`, so "no `.bin` left" is the reliable success test (a Python traceback goes to stderr, which neither `pythonLog.txt` nor the API `output` captures).
- Exports land in `<path dir>/city/<name>.psdl` (game folder layout from `output_layout.py`; tune, race, geometry, bound, texture, jpg go next to `city`).
- All PATHSET writers (props, decals, race props, parked cars, trains and boats) run under the `pathset` flag, independently of `cinfo_aimap`. Each city-route writer has its own error guard. Files written again are truncated or replaced, including shorter outputs; repeat-export checks are in `exporters/psdl/tools/_test_export_overwrite.py`.
- The bundled Python needs `pythonInfo/requirements.txt` (e.g. Pillow for the hudmap). CLI sessions skip the builder's Python check, so install them by hand.

## Custom elements

Most MM2 custom elements are the PSDL attributes, the others are the decals and trains (the generic mechanism is in the builder's `wiki/Core-Custom-Elements.md`, the decals and trains in the README). Equivalence check: export, convert everything, export again, compare PSDL room by room and BAI. The expected result is 0 differences.

### PSDL attributes

The PSDL attributes are for testing, so the README doesn't document them. They are `creatable: false` (no Create menu entry) and the `ui.json` of the `psdl` types has no `convert:toPsdl` button: they are made by the `toPsdl` converter (API `elements.convert`), the importer (`Scripts → Import MM2 city`) and `customElement.create`.

- Roads, intersections, terrain patches and building lines of type `psdl` (not exported to PKG) can be converted to the PSDL attributes they are exported to (converter `toPsdl`, run with the scripting API `elements.convert`), to edit them one by one: each vertex of the PSDL is a control point. Converting doesn't change the export: the converter runs the exporter on the element and turns the parts it would write into the attributes.
- The attributes are in rooms (one per room of the element), each room a block of the PSDL; the parts of a building are in a group placed in the room where the building is when exported (Scripts > Assign building parts to rooms merges them into their rooms). The roads and intersections also get their BAI road or intersection, which can be edited too (lanes, rules, connections).
- A converted room gets its perimeter as the exporter follows it (with `simplifyPerimeter`). Since it is set, changing the shape of its contents (e.g. adding sections to a road) needs the perimeter to be computed again (Compute the perimeter from the contents, in the panel of the room) or removed.
- The BAI road of a converted road is Auto-calculated: when the road attributes converted with it are edited, its edges and curbs follow theirs (chained from room to room) and its lanes (as many as there are) are spread evenly between each curb and the middle of the road (or the dividers), as the exporter does when the lanes drawn in the editor can't be used. Its points can't be edited while it's on: uncheck Auto-calculated to edit them (the road attributes are then edited alone).
- The points of a converted building follow each other: the points above another one are on its vertical line, and the lowest points inside the top or bottom edge of a sliver or facade bound (the corners of the facades between the ends of a side) are on that edge, so moving a corner keeps the building together.
- A converted road gets the psdl props containers of its prop rule (the ghost keeps exporting the others).
- The converted roads and intersections stay as hidden ghosts, so that the other elements keep their shape; the panel of an attribute can bring the original element back.
- The `psdl` road type gives its intersections an anchor across each of its ends (`endAnchors`: the outer sidewalk edges, the curbs at road level and, with a divider, its sides), so all the points of the end section of a converted road stay on a procedural intersection and follow it.
- The dividers at the ends of a converted divided road follow the line between the curbs there (which it shares with the converted intersection), so they keep their places across the road when the intersection, or its room, is moved.
- Triangle fans, road triangle fans and roof triangle fans can be converted to each other. Road and roof fans keep all their vertices at the same height, facades stay vertical rectangles, the tops of facade bounds and slivers stay horizontal.
- The texture references are not elements: the exporter makes them from the textures of the attributes.
- The types are the attributes of the rooms of the PSDL (see the [file format](https://github.com/Dummiesman/angel-file-formats/blob/master/Midtown%20Madness%202/Room_attributes.md)) and the BAI elements; the control points are the vertices of the PSDL, the heights of the PSDL (facades, roofs, slivers) come from the positions of the points when exported:

  | Type | Attribute | Points |

  | `room` | A room (block) of the PSDL: contains the attributes and the BAI elements. Echo, warp, hudmap category. ## Midtown Madness 2 reference

Facts reverse-engineered from `midtown2.exe` and the stock files. They explain why exporter limits and workarounds exist.

**Engine limits and crashes** (first stop: `mm2.log` and `mm2hook.log` in the game folder):

| Symptom | Meaning |
|---|---|
| Ambient traffic crash (~0x53A0D2) | A BAI intersection with **> 11 roads** overflows a 10-entry stack array. The BAI writer warns (`MAX_INTERSECTION_ROADS = 11`) and json_processor splits such intersections into a ring of small BAI intersections (with a `key` property) |
| Crash 0x45da58 after "Placing props along road segments" | A room with a prop rule uses a texture index **>= 255**. The writer orders materials so prop-rule blocks come first and drops the props of blocks still over the limit |
| Crash 0x4a48d8 after "Loading objects", then FindHeap failed | Static geometry table overflow: **~600-650 unique INST/prop mesh names** (6 slots each, ~4096 total, no bounds check). `inst_writer` warns at 597 |
| `PHYS.DeclareMover : mover not even in city` | The player car is outside any PSDL room, one line per frame |
| `Vehicle %d did not have permission to traverse intersection` | FIFO road-end rule (0) violation. Stock SF uses FIFO only at 3-way ends |
| Crash 0x5440c5 (aiPath lane vehicle update) | Lane vehicle count larger than the linked list. Cause not pinned down |
| PSDL perimeter spikes | Fixed in `psdl_writer` (`remove_spikes`). Lowering the area threshold is **not** the fix. Lint with `psdl_check.py` |

Other limits: 511 unique textures per city. PSDL has no per-vertex UVs and max 65536 vertices. The PSDL texture count is names + 1.

**Pedestrians (BAI sidewalks):** the walk target is evaluated 6 m ahead on an **unclamped** Hermite curve, so short sidewalk segments that turn make pedestrians fly off and circle. Segments touching a sharp corner need to be ≥ ~16 m. `bai_writer.spread_corner_points` moves only the sidewalk points; the 2 m car sections stay.

**BAI:** coordinates are (x, up, z) with x mirrored. The engine's room lookup returns the first intersection of a room before its roads, so don't put extra intersections in road rooms. For stock BAI derivation rules see the maintainer's psdl-viewer project, `Scripts/Formats/BaiFile.cs` (location in the builder's `CLAUDE.local.md`).

**Decals (`city/<city>/decals.pathset`, PTH1):** one path per decal, named after its texture (≤ 31 chars). It is drawn as one triangle strip of point pairs, lifted +0.01 m. U is 0/1 alternating, and V of pair k = round(|p[2k]-p[0]| / |p[0]-p[1]|), so pairs must sit at about whole tile distances. The decal is attached to the room containing midpoint(p0, p2) and drawn only when that room is visible, so split long strips. Winding: ((p1-p0)×(p2-p0)).y > 0 in MM2 coordinates. Paths with fewer than 3 points are skipped.

**Hudmap and menu maps:** `geometry/hudmap_<city>.pkg` uses chunk `H` with FVF 0x102 and one quad per tile at y=0. **`.tex` rows are stored bottom-up**, so flip a north-up image before writing. `tune/<city>.mmHudMap` holds the `Ocean Color` as RGB 0..1. Menu maps are `jpg/<city>_map*.jpg`, 242x184, with the map in about (8,5)-(236,179). An optional frame goes in `Files/common/MidtownMadness2/jpg/mapframe.jpg`. Map labels appear only on the jpgs.

**Props (bangers):** the game draws a banger at `position + rotation * CG` (`CG` of `tune/banger/<pkg>.dgBangerData`, MM2 coordinates, x mirrored in the builder), for the pathset props, the prop rules and the traffic lights; without banger data at the position. The editor does the same through `server/mesh_transforms.py` (the builder's `meshTransform` placement rule), so the exported position is the placement point. A mesh without a `.dgBangerData` gets no transform (`None`), so the editor falls back to `autoYOffset` (lowest point on the placement point). The CG is usually `-minY` of the mesh, but not always (fences are drawn from one end, `sp_cenotaph_gen_l` 4 m forward, `sp_chinagate_f` has CG 0 and sinks 7 m). Same rule as the psdl-viewer's `BangerTransform`.

**Pathset line paths (type 2)**, from the walker `466d40` (SHA256 in "Train splines", not run in game): each span gets a matrix with X = the normalized direction to the next point (including its slope), Z = direction x up. So the model's own X axis lies along the path: stock `sp_barricadeconcr_f` is 5.00 m on X with 5 m spacing. The step is stretched to fill the span: `step = length / floor(length / spacing)`, and a span shorter than the spacing gets no props. `prop_rows.pathset` and `_test_prop_placers.native_positions` follow this; the psdl-viewer still uses the exact spacing with at least one prop per span. The editor preview applies only the yaw, not the slope. A pathset holds at most **192 paths**: the set is 0x310 bytes with the path pointers from +4 and the count at +0x304, and the loader `467210` has no bounds check, so path 193 overwrites the count (the stock maximum is 144 in SF's `props.pathset`). `PATHSETWriter` and `parked_car_export.py` report an error above this and write the first 192. Each prop line is its own record.

**Parked cars:** `race\<city>\<city>_parkedcar[_<mode><n>].pathset` (loader `415940`, variant first), type-2 paths, written by the exporter for the `parkedCars` props type (see "City importer and prop placers"). Manager load `579af0`: the spacing is forced to 5 m when below 5, and path names are never read (`PATHnn`, or `sp_pcar03_l` in `london_parkedcar_crash0`, change nothing). Callback `579bd0` for each slot: `rand() % 3`, where 0 leaves the slot empty and 1 or 2 creates `giz_pcar01_l` or `giz_pcar02_l`, rotated 90 degrees around Y so that model Z lies along the path. The game doesn't look for the ground (static reading of `466d40`, `579bd0` and the banger init `441c30`): a car is at the height of the path, plus the rotated CG. The exporter makes that height the one projected in the editor, as each slot is the first point of its own span. The rotation is applied to the path axes, so the model Z stays horizontal and a sloped span rolls the car sideways instead of pitching it; the stock spans stay almost flat (at most 0.3 degrees in SF, 3.8 in London). The second `rand()` of the callback picks the paint job (`442a10`: modulo the count of the model, 9 for `giz_pcar01_l`/`giz_pcar02_l` and 10 for `giz_pcar03_l`). Without MM2Hook `giz_pcar03_l` is never picked. `rand` (`4bbdf0`) is a linear congruential generator whose main seed is never taken from the clock: the game constructor sets it to 1 (`4068f0`, saved at `+0x6d8` by `406990`), and the clock-based seeds at `424d46`/`424dc4` run on a second stream, swapped in and out by `4bbd50`/`4bbd80`. So the layout should shift if something changes the number of `rand` calls before the load (static reading). Checked in game on the maintainer's `testp` city: the cars lie along the path and head in its direction, a sloped span rolls them sideways, and the layout repeats between launches. MM2Hook (`dinput.dll`) changes this, with both options on by default in its `mm2hook.ini`, so check the hook as well as the exe when the game differs from a static reading. `UseAllParkedCars` patches `579be1` to `rand() % 4`, so 1 in 4 slots is empty and the other three each get `giz_pcar01_l`, `giz_pcar02_l` or `giz_pcar03_l`. `DynamicParkedCarDensity` replaces the callback pushed at `579b80`: in roam (Cruise) only, a slot is skipped when `frand()` is at or above the traffic density (mode at `6276f8`, density at `+8`). A kept slot restores the seed and a skipped one doesn't, so moving the slider also reshuffles the slots after each skipped one. No traffic means no parked cars, and in the other modes the density has no effect. Its `RandomSeed` option (`0` by default, `-1` always random) should also end the repeating layout, according to its description. `giz_pcar03_l` is 5.49 m long (`giz_pcar01_l` 5.12, `giz_pcar02_l` 4.10), so it overlaps at the stock 5 m spacing as well as at the 5.25 m minimum of the props type. `413210` skips the manager when flag `6b16fc` is set (it also skips the ferry; it looks like multiplayer, unconfirmed) and the mode is roam or multicop. Other stock uses are ordinary pathset props, so X lies along the path: `giz_pcar01_l`/`giz_pcar03_l` in London's `crash*.pathset` (spacing 40 m) and `sp_pcar0n_l` in `slalom.pathset` (20 m). `giz_pcar01_l` has the same 2.31 x 5.12 m footprint as `sp_pcar01_l`, but with four LODs, two banger parts and a much higher `ImpulseLimit2` (8000000 against 635600).

**Textures and slivers:** facade/sliver V runs from the top (v=0 = texture top in the editor; the psdl-viewer uses the flipped convention). Game sliver rule: u = floor(len·s + 0.5), v = (top - y)·s. Stock sliver scales are always positive. Stock city PKGs use byte shaders `0x81` with colours 229/229/0 and shininess 0.25.

**Stock data:** SF cable cars are BAI `nTrams` = 1 on both sides, with the rail 2.5 m from the centre line. London's visible trains are `gizTrain` gizmos from `race/london/london_train.pathset`. Stock cities are compressed about 0.3-0.5x relative to real scale.

Reverse-engineering setup: install capstone + pefile with `pip install --target <scratch dir>`. Don't name a script `dis.py`, because it shadows the stdlib module capstone imports.

## City importer and prop placers

`Scripts → Import MM2 city` lives in `scripts/importCity`. `_formats.py` is bounded binary reading, `_mapping.py` creates converter-shaped custom element payloads, `_companions.py` handles CSV/settings/transforms, and `main.py` is the transactional API adapter. Unknown attribute sizes fail rather than guessing. The viewer-derived readers retain `LICENSE-viewer.txt`.

PSDL type 1 stores regular sidewalk pairs as **inner, outer**. Exactly four references beginning with `0,0` or `1,1` describe an end cap: the first pair is a marker (start/end), not city vertices, and the last pair maps to `sidewalkCap.a/b`, with `which` 1/2. Treating these as regular strips pulls geometry toward vertices 0/1. `_test_sidewalks.py` runs through the builder script CLI with `KM2_IMPORT_TEST_FOLDER`; optional `KM2_MM2_SOURCE_ROOT` adds ten fixed-seed SF/London sidewalk attributes. It checks generated geometry, undo/redo, save/reload and native PSDL re-export without loading a whole stock city.

The `propLine` and `propPolygon` custom elements use the generic `settings.propPlacer` capability (builder wiki `Core-Prop-Placers`). The `propLine` strip is `inline` (its props are in its panel, its one preset is the element's) with all the top-level props types of `elements/props/types`. `exporters/psdl/prop_placers.py` chooses by the props type of `propRule.main`: `pathsetStrip` (`lineOnly`, no width, spacing in metres) is exported as native PATHSET type 2, with the byte spacing. With **Project to ground** off the path is the evaluated `spline.sections`. With it on, each prop is projected as with the other types and the path has a point at each one, plus the end of the line (a placement without a model): the game doesn't look for the ground, as for the parked cars. So each span must hold exactly one prop: at least the spacing and shorter than twice it. `prop_rows.pathset` counts the props on the plan, so the ground can't make a span shorter than the spacing, and `path_on_ground` extends by 1 mm the spans that single precision makes shorter (keep the spacing byte exact: rounding it down would double every prop at 0.5 m). Spans of twice the spacing or more get a warning. The `line` type ("Custom line") is separate: `line` puts model Z along the path and exports individual props, `pathsetStrip` puts model X along the path as the game's type 2 does, so one preset can't mean both. On a prop line `line` is `lineOnly` and `authoredLine`, so it walks the spline as authored and only the height of each prop comes from the ground (a curved spline is projected at its sections, and walking that line made the spacing depend on the ground). Its props stay level in game: a type 1 path can't pitch (the walker zeroes the height of the direction, `466dee`), a type 2 path has model X on the span, and an INST would pitch but isn't a banger, so it couldn't be knocked over. A "follow the ground" option was removed for this reason (maintainer decision). The other `data.propLines` placements and those of the polygons always export individually, regardless of the PSDL type. Preserve separate native records for identical models/spacing. `tools/_test_prop_placers.py` checks migration and the actual BIN/PATHSET writer pipeline; `--preview <export-json>` audits editor placement parity. Builder focus: `KM2_SELFTEST_FOCUS=propPlacers`.

Migration 5 holds all the format changes since core version 4. It removes the experimental standalone records before decoding with backups, preserving shared points and ordinary/converted road rules. Obsolete names are recognized only by that migration and its fixtures; there is no builder compatibility type, API or serialized collection.

Migration 5 also converts old `pathsetStrip` containers (`elements` list, `rawSpacing` byte) on any element, and moves to the single props types of the builder (`elements/props/types`, builder wiki `Core-Props-and-Objects`). `line`, `parkedCars` and `pathsetStrip` containers become flat states. The groups `psdl`, `custom` and `mixed` keep their `elements`, whose `psdl` and `custom` entries become `psdlProp` and `customProp` (`nestedOnly`). It finds them by position, the values of any `propRule` and the values of the `roadPropRule` presets, because a road state and those presets have a `type: psdl` of their own. The `propContainer` and `propElem` presets move to `props/<type>`: a container and an element with the same name in the same category get a suffix on the second, and the states linked to it are relinked.

The rows of the MM2 prop rules are in `lua/prop_rows.lua`, the `placement` callback of `line`, `customProp`, `psdlProp` and `pathsetStrip`. The positions must stay those of existing cities and the exporters write them, so keep its order of evaluation. It uses `rnd` with seed 0, shared with the other rows of the element, for the position across and then the mesh, also in the iteration that ends a row; `ctx.random` would give other values. Sums go through `single`, as the expressions the rows used to be in were single precision.

The `parkedCars` props type (road containers and prop lines, `lua/parked_cars.lua`) exports through `exporters/psdl/parked_car_export.py`, called with the boats under the `pathset` flag, and is skipped by `get_road_props` and `export_prop_placer`. It is `lineOnly` with a `boundsOnly` `xPos`, so on a prop line the row is on the spline (no width or X position), while a road row keeps its X position. It isn't `authoredLine`, so it walks the projected spline. Its preview is an example that always shows the first paint job. It follows the stock game (two models, 1 in 3 slots left empty), or the MM2Hook defaults (three models, 1 in 4) when the `assumeMM2Hook` city property is on. That property is off by default, injected on roads and custom elements, and meant for anything else in the core that differs with the hook. It also enables editing the roll (`rollRequires` of the road types: editing only, so a roll already set still applies and exports, and the API can set it) and selects the PSDL warnings about texture references (`report_high_materials`, checked by `_test_psdl_warnings.py`). The type gives a placement for each slot, with no model for the empty ones (`meshId` -1 in `data.propLines`, which the other exporters skip with `utils.placed_props`), so the exporter reads all of them and takes the direction from their rotation. A row is one path with a vertex at each slot and a closing vertex, and a spacing byte such that `floor(span / spacing)` is 1 for every span. Keep each span at 5 m or more, as the game raises a lower spacing to 5 m. The game puts model Z along the path direction, so the exporter reverses a row whose first slot forward opposes it. The default `forward` is `-localForward`, which follows the traffic of the nearest lanes (`line` uses the opposite). On a road row `driveOnLeft` turns it around with the lanes; a prop line (`ctx.placer`) has no lanes and stays against its spline. A race file holds the race's rows and then the city's, because it replaces the main file. Its names are in the `.km2-parked-car-races.json` manifest, so only exporter-owned files are removed. Checks: `python exporters/psdl/tools/_test_parked_cars.py`, builder `KM2_SELFTEST_FOCUS=propPlacers`.

`parkedCar` is the single-slot point custom element in Create > Props. Its internal `propRule.main` uses the nested-only `parkedCar` props type and `parked_cars.single`, always showing `giz_pcar01_l` as an example, without a mesh field. `parked_cars.singleGeometry` turns the authored center point and its yaw into a short horizontal props line. Both parked-car props types go through `parked_car_export.py`; a single slot uses the existing 6 m closing span, one of the same 192 paths. All three race types include it in their accepted types and Props contents. Its `point.project` is false: height is editable and the normal point editor exposes a one-shot **Project to ground** button, as for mesh instances. Moving, loading or changing a surface does not automatically project it. The implementation stays in the core.

BAI remains approximate: report lost room memberships and train splines; do not advertise complete stock round-trip equivalence from close lane geometry. `_roundtrip_check.py` reports pedestrian displacement separately. Keep stock checks bounded (five fixed-seed routes per city) and assets/output in scratch folders. The importer adds asset search paths outside undo and references source files without copying them.

## Spline decals

`elements/customElements/decal` uses the generic spline evaluator and road JSON components, API kind `customElement`, points `spline`. `spline.pieces` in exported elements supplies unlifted strip edge pairs; `json_processor.get_decals` passes these as DECAL parts with `strip_pairs=1`. The writer also accepts the older centerline/width input used by existing fixtures. Core component UVs follow the game winding and rounded distance of the first pair; height offset is 0.01 m. Keep projection away from overlay layer 13 to avoid accumulating height on overlapping decals.

`elements/customElements/decalSingle` is the generic point kind (`point` setting: one `center` point, the gizmo on the element with no handle, yaw only, scalable on X and Z, projected on the surface like the spline decal points (`projectionMask` 136), builder wiki `Core-Custom-Elements`, "Point elements"): `lua/decals.single` builds the quad from `ctx.points.center`, `ctx.rotations.center` (euler degrees, applied Z, X, Y; positive X pitch tips the front down) and `ctx.scales.center` (X = width, Z = length), with the strip vertex order of the spline decals (start pair then end pair, U 1 then 0, V = round(length/width) at the end pair, lifted 0.01 m). `json_processor.get_single_decal` recomputes the same four corners from the exported `points.center` (`decal_single_corners`, keep it in sync with the Lua) and emits one `0_DECAL` with `strip_pairs=1`; it warns above 25 m (the game picks the room of midpoint(p0, p2)) and for a mirrored quad. Both decal types use `createMenu.submenu` `DECALS_MENU` and `createMenu.label` (short "Single"/"Spline" in the menu, `ui.label` is the full "Decal (single)"/"Decal (spline)"). Tested by `_test_decals.py` and the builder's `SingleDecals` self-test (`KM2_SELFTEST_FOCUS=splines`).

`converters/generateRailDecals` is non-replacing and creates independent low-poly decal splines across the selected intersection only. `lua/decals.canGenerateRails` controls button availability. Pairing uses the existing BAI `join_rails` rules. Repeated generation deliberately appends; users delete old decals manually. Migration 3 converts manual city-property decals and removes automatic rail settings without baking them. Update new-city template coreVersion with the core migration version. Focused synthetic checks: `python exporters/psdl/tools/_test_decals.py`; keep stock assets out of fixtures.

The focused builder integration uses `KM2_SELFTEST_FOCUS=splines` with `selftest api <new folder>` (about 6 s windowed). To compare preview geometry/UVs with a real exported PATHSET, use `python exporters/psdl/tools/_test_decals.py --preview <export-json file> <decals.pathset>`.

## Low LOD road textures

`converters/generateLodTexture` (`replace: false`, button in the `ui.json` of the `psdl` road, enabled by `lua/psdl.canGenerateLodTexture`) composes `textureLOD` and sets it on the road through a converter `updates` entry; the file is written outside undo. The layout is measured on the stock `*_lo_f` textures: square, 64x64, type 17, one mip, the road along X, and across it the sidewalk, the half road (`texture1`, its top row at the curb, its bottom row at the center), the divider, then the same bands mirrored, in proportion to their real widths. Along the road each tile is as long as its band is wide, as in `RoadSection` of the psdl-viewer, rounded to whole tiles per texture so that it repeats (so `r6_f` on a 40 m road gives 9 dashes against the 8 of `r6_lo_f`, drawn by hand). The texture covers the whole road only with real sidewalks: flat shoulders are not part of the 0x00 road attribute. The name holds a hash of the pixels, so equal results share one file and a changed result can't show a cached texture.

`_fa` is a darker version of 74 stock textures (roads, sidewalks, decals). The suffix is next to `_ni` in the exe, at `0x1c56a4`, but when the game uses it hasn't been established. The generator writes one when the road texture has one, from the `_fa` of each source (or the plain one). `exporters/psdl/tools/_test_lod_texture.py` has the synthetic checks; builder coverage is `LodTextureGeneration`, `KM2_SELFTEST_FOCUS=splines`. Not checked in game yet.

## Map label previews

Map labels are point custom elements (`mapLabel`, `points.center`) owned by the city-properties singleton `elementContainer`, category `hudmap`, activated by the `CP_HUDMAP` tab. The shared container machinery handles visibility, contextual creation, contents and undo. `lua/map_labels.lua` builds the glyph mesh and its outline from `lua/map_label_font.lua`, generated from the bundled OFL Liberation Sans Bold font by `tools/_generate_map_label_font.py` (development-only fonttools/shapely/mapbox-earcut). The generic `GeometryMesh.color` uses an opaque, unshaded two-sided material. The preview is an editor aid, not a preview of the final map: white text and, 2 cm under it, a black outline (0.05 em, a strip around the edges used by one triangle with round joins at the outer corners, from the clockwise triangles of the glyphs, cached per glyph), with `castShadows` off. From below the ground the outline shows a little through the sharp notches of the letters. The preview alone is raised 5 m; markers and authored controls stay on the ground. The point follows the surfaces (`point.project`), also when loaded. `ctx.parameters` supplies the text, and injected `hudmapMetersPerPixel` supplies scale. The Labels colour is only for the exported maps. The same bundled font is the export default, with four-times label supersampling and 75% size on roam maps. Measured stock style: ink darkens every background by the same factor (black, `LABEL_OPACITY` 0.5, not an opaque grey), default size 6.75 px (cap height 5 px), `LABEL_TRACKING` 0.12 em, markers over labels, JPEGs 4:4:4 at quality 98. `lua/map_labels.lua` keeps its own copy of the size and tracking, so change both. Stock race maps are crops at a fixed zoom per city (roam/race about 0.76 in SF, 0.66 in London, and the London JPGs are squashed vertically against the tiles); the exporter frames each race and uses a fixed 0.75, so label size against the map still differs from stock. An explicit export font override does not replace the bundled preview outlines. Latin/Latin Extended A and common punctuation have generated glyphs; other preview characters use the missing-glyph box while exports retain the full text.

Migration 5 moves legacy `cityProperties.mapLabels` to owned point elements with backups, preserving text, size, angle, map filters and positions. The exporter also accepts legacy standalone JSON. Native HUD tiles and `<city>_hudmap_preview.png` stay label-free; `<city>_hudmap_labels_preview.png` uses All/Roam names. Previews stay outside AR files. Checks: `python exporters/psdl/tools/_test_hudmap.py [builder-export.json] [--stock-archive MM2TEX.AR]`, builder `KM2_SELFTEST_FOCUS=mapLabels`. The optional stock check reads only three known visible words from SF/London JPGs, checking width and cap height within JPEG tolerance (it can't see opacity or letter shapes; the synthetic tests cover the ink, marker order and JPEG sampling). The exact original face cannot be proven from those raster images; describe this as stock-style rendering, not bit-identical reproduction. No stock image or original game font is bundled. Font/source/license details: `fonts/README.md`.

## Instance state of the splines

The values of a road's spline (`project`, `projectAll`, `curveType`, `segments`, `segmentsPer100m`, `lpf`, `adjustLowPolyWidth`, `makeCoplanar`, `hermiteTension`, `subdivideEqually`), `warp` on roads and intersections, and `projectToGround` on building lines are in the instance state, so presets don't carry or change them. The initial values are in `elements/roads/*/settings.json` and `elements/buildings/psdl/line_settings.json`, and match what the templates used to set. `warp` on roads has `reuseInNewRoads`, so a road drawn in the editor takes it from the last road selected, with the spline values. Terrain patches keep `warp` and `projectToGround` in their state, because they have no presets. Spline custom elements keep these values in their single state, excluded from presets, and the decal's Bézier default moved from its preset to `spline.defaultCurveType`.

Migration 5 moves the values of the existing elements and removes them from the presets, only under the listed spline types for `customElement/<type>` (another type can have its own `segments`). A key that is missing stays missing, so it reads as before. Equivalence check: export an old city with the old build, migrate a copy, export again and compare PSDL, BAI and INST (0 differences expected). Checks: `python exporters/psdl/tools/_test_spline_state_migration.py`, builder `KM2_SELFTEST_FOCUS=splineState`.

## Boat paths (boats, ducks, ferry)

`elements/customElements/boat` (one type; the `model` enum and `speed` float, curve ID 4 `mm2Boat`, `lua/boats.lua`, `spline.closed`) exports `race/<city>/<city>_sailboat.pathset` and `<city>_ferry.pathset` with `exporters/psdl/boat_export.py` (called next to `export_trains` under the `pathset` flag; both share `route_pathset.write_routes`). Export the authored `points.spline` (X mirrored), at least three points, room 0, type 2. Checks: `python exporters/psdl/tools/_test_boats.py`; builder `KM2_SELFTEST_FOCUS=boats` with `selftest api <new folder>` (also covers the generic `closed` spline setting). There is no importer for these paths and no race variants (`<city>_sailboat_<racetype>_<n>.pathset`, tried first by the game).

Reverse-engineered from the same executable as the trains (SHA256 `992c53c9250cf822b44bf4a4013bd5805229bbbeb7b478a4c2556531bc5340f3`), not run in game:
- Managers are created at `413210`: `(default model, name)` = (`giz_sailboat01_f`, `sailboat`), (`giz_bridge01_l`, `bridge`), (`va_ug_l`, `train`), (`giz_carferry01_f`, `ferry`), (`giz_pcar`, `parkedcar`). The sailboat loader `415240` and the ferry loader `415780` read `race\<city>\<city>_<name>[_<race type>_<race number>].pathset` (variant first, then without the suffix) with `467210` (PTH1: count, current path; per path a name32, point count, one unknown uint32, points of room uint32 + x, y, z, then type, spacing and 2 padding bytes; `466bd0` stores spacing / 4 at path+0x34).
- Model: for each path `geometry/<path name>.pkg` is used if the file exists (`4c59e0`), otherwise the default model of the manager (so `PATHn` is a sailboat). Stock names: `giz_sailboard01_f`, `giz_duck_s`, `giz_tug01_l`, `giz_watertaxi01_l`, `giz_carferry01_l`. There is no model-specific code in the sailboat manager: ducks and boats differ only in model, spacing and path.
- Movement: the sailboat objects (`578410`) use the train follower (`57A050`/`57A410`: `57A530` tangents = 0.5 x half-differences, `57A370` cubic on X, Y and Z, no Y override), advanced by a fixed 1/60 s per update, with speed constant along each span. The segment index wraps (`57A6D0`/`57A710`) and nothing stops it, so every route is a closed loop. The room is recomputed from the position (`465480`), so the room field of the points is unused (the stock files have real ones).
- Speed of the sailboat manager (`578707`): random in [spacing / 4 - 1, spacing / 4 + 1] m/s per object (stock: ducks 8 = 2 m/s, boats and tugs 20 = 5 m/s, sailboards 80 and 120 = 20 and 30 m/s). The ferry manager (`579910`) randomises `0.75 +- 0` for every path, so the spacing is not read (stock 20); in game it is still to be checked. The parked cars are not moving objects (see "Parked cars" in the Midtown Madness 2 reference).
- Open: the unknown per-path uint32 (29 in the SF ferry, 3 in one London duck path), the type-1 "directed points" paths of London's ferry, the room-height Y offset added by the ferry/train update (`5794d0`/`578aad`) that the sailboat update lacks, and the bridge manager (`415400`, `open:`/`inactive:` prefixes).
