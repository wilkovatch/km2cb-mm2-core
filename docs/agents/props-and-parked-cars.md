# Props, INST and parked cars

Read the [repository instructions](../../AGENTS.md) first. Paths and command examples below are relative to this repository root unless another working directory is specified. Builder CLI and self-test commands run from the builder root.

Also read [Exporter workflow and engine limits](exporting.md) for shared limits and PATHSET flags. Race ownership is covered in [Races and state](races-and-state.md#race-containers-and-opponents); independent parked-car points use the [point-state migration](races-and-state.md#independent-point-values).

## Native prop and INST reference

**Props (bangers):** the game draws a banger at `position + rotation * CG` (`CG` of `tune/banger/<pkg>.dgBangerData`, MM2 coordinates, x mirrored in the builder), for the pathset props, the prop rules and the traffic lights; without banger data at the position. The editor does the same through `server/mesh_transforms.py` (the builder's `meshTransform` placement rule), so the exported position is the placement point. A mesh without a `.dgBangerData` gets no transform (`None`), so the editor falls back to `autoYOffset` (lowest point on the placement point). The CG is usually `-minY` of the mesh, but not always (fences are drawn from one end, `sp_cenotaph_gen_l` 4 m forward, `sp_chinagate_f` has CG 0 and sinks 7 m). Same rule as the psdl-viewer's `BangerTransform`.

**INST modifiers**, from the loader `4656f0` (same executable as [Train splines](trains-and-boats.md#train-splines), static reading, not run in game): the u16 is the paint job in the low byte (passed to a virtual call at `46598e`, stock facades use 0 to 12) and the flags in the high byte. `0x01` Landmark, `0x02` Banger, `0x04` no wheel collision, `0x20` Multiroom; the loader reads no other bit, so migration 7 drops them. Banger is tested first and creates a banger (`465861`), but the Landmark steps after it still run on that banger (`465991`). The wheel collision bit is read only in the Landmark branch (`4658a1`). Multiroom places the instance room by room (`467c40`) only without Landmark (`465ac2`). That function appears to use the bound without a null check, so a Multiroom mesh without a bound may crash (unconfirmed, and the exporter can't check, as bounds aren't in the user-provided files). Stock: `0x0100` on monuments (88 in SF, 176 in London, all simple records), `0x2000` only on `nw_bwaytunnel_f` and `sw_subway_b4_10_l`, and Banger and the wheel collision bit never in `sf.inst` or `london.inst`. The `instMesh` parameters are `instLandmark` (on by default, through `defaultValue`), `instSimpleCollision`, `instBanger`, `instMultiroom` and `instPaintJob`; parametric objects and PKG groups are always Landmark. `json_processor.get_inst_modifiers` warns about the combinations above. Checks: `python exporters/psdl/tools/_test_inst_modifiers.py`.

**Pathset line paths (type 2)**, from the walker `466d40` (SHA256 in [Train splines](trains-and-boats.md#train-splines), not run in game): each span gets a matrix with X = the normalized direction to the next point (including its slope), Z = direction x up. So the model's own X axis lies along the path: stock `sp_barricadeconcr_f` is 5.00 m on X with 5 m spacing. The step is stretched to fill the span: `step = length / floor(length / spacing)`, and a span shorter than the spacing gets no props. `prop_rows.pathset` and `_test_prop_placers.native_positions` follow this; the psdl-viewer still uses the exact spacing with at least one prop per span. The editor preview applies only the yaw, not the slope. A pathset holds at most **192 paths**: the set is 0x310 bytes with the path pointers from +4 and the count at +0x304, and the loader `467210` has no bounds check, so path 193 overwrites the count (the stock maximum is 144 in SF's `props.pathset`). `PATHSETWriter` and `parked_car_export.py` report an error above this and write the first 192. Each prop line is its own record.

**Parked cars:** `race\<city>\<city>_parkedcar[_<mode><n>].pathset` (loader `415940`, variant first), type-2 paths, written by the exporter for the `parkedCars` props type (see [Prop placers and placement rules](#prop-placers-and-placement-rules)). Manager load `579af0`: the spacing is forced to 5 m when below 5, and path names are never read (`PATHnn`, or `sp_pcar03_l` in `london_parkedcar_crash0`, change nothing). Callback `579bd0` for each slot: `rand() % 3`, where 0 leaves the slot empty and 1 or 2 creates `giz_pcar01_l` or `giz_pcar02_l`, rotated 90 degrees around Y so that model Z lies along the path. The game doesn't look for the ground (static reading of `466d40`, `579bd0` and the banger init `441c30`): a car is at the height of the path, plus the rotated CG. The exporter makes that height the one projected in the editor, as each slot is the first point of its own span. The rotation is applied to the path axes, so the model Z stays horizontal and a sloped span rolls the car sideways instead of pitching it; the stock spans stay almost flat (at most 0.3 degrees in SF, 3.8 in London). The second `rand()` of the callback picks the paint job (`442a10`: modulo the count of the model, 9 for `giz_pcar01_l`/`giz_pcar02_l` and 10 for `giz_pcar03_l`). Without MM2Hook `giz_pcar03_l` is never picked. `rand` (`4bbdf0`) is a linear congruential generator whose main seed is never taken from the clock: the game constructor sets it to 1 (`4068f0`, saved at `+0x6d8` by `406990`), and the clock-based seeds at `424d46`/`424dc4` run on a second stream, swapped in and out by `4bbd50`/`4bbd80`. So the layout should shift if something changes the number of `rand` calls before the load (static reading). Checked in game on the maintainer's `testp` city: the cars lie along the path and head in its direction, a sloped span rolls them sideways, and the layout repeats between launches. MM2Hook (`dinput.dll`) changes this, with both options on by default in its `mm2hook.ini`, so check the hook as well as the exe when the game differs from a static reading. `UseAllParkedCars` patches `579be1` to `rand() % 4`, so 1 in 4 slots is empty and the other three each get `giz_pcar01_l`, `giz_pcar02_l` or `giz_pcar03_l`. `DynamicParkedCarDensity` replaces the callback pushed at `579b80`: in roam (Cruise) only, a slot is skipped when `frand()` is at or above the traffic density (mode at `6276f8`, density at `+8`). A kept slot restores the seed and a skipped one doesn't, so moving the slider also reshuffles the slots after each skipped one. No traffic means no parked cars, and in the other modes the density has no effect. Its `RandomSeed` option (`0` by default, `-1` always random) should also end the repeating layout, according to its description. `giz_pcar03_l` is 5.49 m long (`giz_pcar01_l` 5.12, `giz_pcar02_l` 4.10), so it overlaps at the stock 5 m spacing as well as at the 5.25 m minimum of the props type. `413210` skips the manager when flag `6b16fc` is set (it also skips the ferry; it looks like multiplayer, unconfirmed) and the mode is roam or multicop. Other stock uses are ordinary pathset props, so X lies along the path: `giz_pcar01_l`/`giz_pcar03_l` in London's `crash*.pathset` (spacing 40 m) and `sp_pcar0n_l` in `slalom.pathset` (20 m). `giz_pcar01_l` has the same 2.31 x 5.12 m footprint as `sp_pcar01_l`, but with four LODs, two banger parts and a much higher `ImpulseLimit2` (8000000 against 635600).

## Prop placers and placement rules

The `propLine` and `propPolygon` custom elements use the generic `settings.propPlacer` capability (builder wiki `Core-Prop-Placers`). The `propLine` strip is `inline` (its props are in its panel, its one preset is the element's) with all the top-level props types of `elements/props/types`. `exporters/psdl/prop_placers.py` chooses by the props type of `propRule.main`: `pathsetStrip` (`lineOnly`, no width, spacing in metres) is exported as native PATHSET type 2, with the byte spacing. With **Project to ground** off the path is the evaluated `spline.sections`. With it on, each prop is projected as with the other types and the path has a point at each one, plus the end of the line (a placement without a model): the game doesn't look for the ground, as for the parked cars. So each span must hold exactly one prop: at least the spacing and shorter than twice it. `prop_rows.pathset` counts the props on the plan, so the ground can't make a span shorter than the spacing, and `path_on_ground` extends by 1 mm the spans that single precision makes shorter (keep the spacing byte exact: rounding it down would double every prop at 0.5 m). Spans of twice the spacing or more get a warning. The `line` type ("Custom line") is separate: `line` puts model Z along the path and exports individual props, `pathsetStrip` puts model X along the path as the game's type 2 does, so one preset can't mean both. On a prop line `line` is `lineOnly` and `authoredLine`, so it walks the spline as authored and only the height of each prop comes from the ground (a curved spline is projected at its sections, and walking that line made the spacing depend on the ground). Its props stay level in game: a type 1 path can't pitch (the walker zeroes the height of the direction, `466dee`), a type 2 path has model X on the span, and an INST would pitch but isn't a banger, so it couldn't be knocked over. A "follow the ground" option was removed for this reason (maintainer decision). The other `data.propLines` placements and those of the polygons always export individually, regardless of the PSDL type. Preserve separate native records for identical models/spacing. `tools/_test_prop_placers.py` checks migration and the actual scene/PATHSET writer pipeline; `--preview <export-json>` audits editor placement parity. Builder focus: `KM2_SELFTEST_FOCUS=propPlacers`.

Migration 5 holds all the format changes since core version 4. It removes the experimental standalone records before decoding with backups, preserving shared points and ordinary/converted road rules. Obsolete names are recognized only by that migration and its fixtures; there is no builder compatibility type, API or serialized collection.

Migration 5 also converts old `pathsetStrip` containers (`elements` list, `rawSpacing` byte) on any element, and moves to the single props types of the builder (`elements/props/types`, builder wiki `Core-Props-and-Objects`). `line`, `parkedCars` and `pathsetStrip` containers become flat states. The groups `psdl`, `custom` and `mixed` keep their `elements`, whose `psdl` and `custom` entries become `psdlProp` and `customProp` (`nestedOnly`). It finds them by position, the values of any `propRule` and the values of the `roadPropRule` presets, because a road state and those presets have a `type: psdl` of their own. The `propContainer` and `propElem` presets move to `props/<type>`: a container and an element with the same name in the same category get a suffix on the second, and the states linked to it are relinked.

The rows of the MM2 prop rules are in `lua/prop_rows.lua`, the `placement` callback of `line`, `customProp`, `psdlProp` and `pathsetStrip`. The positions must stay those of existing cities and the exporters write them, so keep its order of evaluation. It uses `rnd` with seed 0, shared with the other rows of the element, for the position across and then the mesh, also in the iteration that ends a row; `ctx.random` would give other values. Sums go through `single`, as the expressions the rows used to be in were single precision.

The `parkedCars` props type (road containers and prop lines, `lua/parked_cars.lua`) exports through `exporters/psdl/parked_car_export.py`, called with the boats under the `pathset` flag, and is skipped by `get_road_props` and `export_prop_placer`. It is `lineOnly` with a `boundsOnly` `xPos`, so on a prop line the row is on the spline (no width or X position), while a road row keeps its X position. It isn't `authoredLine`, so it walks the projected spline. Its preview is an example that always shows the first paint job. It follows the stock game (two models, 1 in 3 slots left empty), or the MM2Hook defaults (three models, 1 in 4) when the `assumeMM2Hook` city property is on. That property is off by default, injected on roads and custom elements, and meant for anything else in the core that differs with the hook. It also enables editing the roll (`rollRequires` of the road types: editing only, so a roll already set still applies and exports, and the API can set it) and selects the PSDL warnings about texture references (`report_high_materials`, checked by `_test_psdl_warnings.py`). The type gives a placement for each slot, with no model for the empty ones (`meshId` -1 in `data.propLines`, which the other exporters skip with `utils.placed_props`), so the exporter reads all of them and takes the direction from their rotation. A row is one path with a vertex at each slot and a closing vertex, and a spacing byte such that `floor(span / spacing)` is 1 for every span. Keep each span at 5 m or more, as the game raises a lower spacing to 5 m. The game puts model Z along the path direction, so the exporter reverses a row whose first slot forward opposes it. The default `forward` is `-localForward`, which follows the traffic of the nearest lanes (`line` uses the opposite). On a road row `driveOnLeft` turns it around with the lanes; a prop line (`ctx.placer`) has no lanes and stays against its spline. A race file holds the race's rows and then the city's, because it replaces the main file. Its names are in the `.km2-parked-car-races.json` manifest, so only exporter-owned files are removed. Checks: `python exporters/psdl/tools/_test_parked_cars.py`, builder `KM2_SELFTEST_FOCUS=propPlacers`.

`parkedCar` is the single-slot point custom element in Create > Props. Its internal `propRule.main` uses the nested-only `parkedCar` props type and `parked_cars.single`, always showing `giz_pcar01_l` as an example, without a mesh field. `parked_cars.singleGeometry` turns the authored center point and its yaw into a short horizontal props line. Both parked-car props types go through `parked_car_export.py`; a single slot uses the existing 6 m closing span, one of the same 192 paths. All three race types include it in their accepted types and Props contents. Its `point.project` is false: height is editable and the normal point editor exposes a one-shot **Project to ground** button, as for mesh instances. Moving, loading or changing a surface does not automatically project it. The implementation stays in the core.
